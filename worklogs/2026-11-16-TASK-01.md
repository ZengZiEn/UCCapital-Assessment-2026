## Obstacles

在 `TASK-01` 的實作與實機驗證過程中，主要遭遇以下四項報錯訊息與工程邏輯挑戰：

1. **障礙一：上層目錄含空白字元導致 `unittest discover` 匯入失敗**
   * **報錯訊息 (Error Log)**：
     ```text
     ImportError: Start directory is not importable: 'c:\\Users\\user\\Desktop\\my datas\\面試相關\\UCCapital\\Q1_Scheduling\\tests'
     ```
   * **原因分析**：工作區路徑中包含空白字元（`my datas`），且初版 `Q1_Scheduling/tests/` 目錄下未建立 `__init__.py`，導致 Python `unittest` 模組在套件探索時無法將 `tests` 視為合法 Package。

2. **障礙二：手算預估之全解空間數量（18 組）與程式窮舉結果不符**
   * **邏輯困難處**：在撰寫初版分析文件時，初步手算預估符合規則的排班表為 18 組；但在執行 `BitmaskMRVSolver.solve_all()` 實機枚舉時，測試斷言 `assertEqual(len(all_schedules), 18)` 失敗，實際回傳了 **34 組** 班表。

3. **障礙三：突發請假時若重新執行全域排班，會造成「班表劇烈震盪（High Churn Rate）」**
   * **邏輯困難處**：當某位員工臨時表示某一天不能上班時，若直接修改其可用性並重跑一次全域求解器，求出的新班表可能與原班表有 3~4 天不同，導致原本沒請假的其他同仁班表也被無故打亂。

4. **障礙四：人類工程師質疑單一高階語言（Python）之直譯器延遲瓶頸**
   * **效能挑戰**：初版 Python `BitmaskMRVSolver.solve_one()` 單次求解耗時約 `27.50 us`。人類工程師（曾子恩）提出質疑：「*做之前的語言選擇是否會影響執行效率？確定效率已經是最好了嗎？*」在量化高頻交易（HFT）場景下，微秒級的 Python 函式呼叫、動態 `sorted()` 與字典建立開銷仍有巨大的底層壓縮空間。

## Resolution

針對上述四項障礙，我們採取了以下具體修復措施與架構升級，並已**向上同步更新**至 [`task.md`](file:///c:/Users/user/Desktop/my%20datas/面試相關/UCCapital/tasks/TASK-01-Scheduling-System/task.md) 與 [`implementation-process.md`](file:///c:/Users/user/Desktop/my%20datas/面試相關/UCCapital/tasks/TASK-01-Scheduling-System/implementation-process.md)：

1. **修復 `unittest` 套件匯入問題**：
   * 於 `Q1_Scheduling/tests/` 補建 `__init__.py` 檔案，並將測試執行指令標準化為 `python -m unittest tests.test_scheduling -v`，徹底解決含空白路徑之匯入報錯。

2. **以實證主義校正全解空間為 34 組（374 種突發請假情境）**：
   * 透過獨立的 `Schedule.validate()` 不變量驗證器對 `solve_all()` 枚舉出的 34 組班表逐一進行合法性檢驗（確認每日恰 1 人、每人 $\le 2$ 天且皆排於可用日），證實全解空間確為 **34 組完全合法的班表**（對應 $34 \times 11 = 374$ 種單日請假測試案例）。同步更新測試斷言與分析文件，並對全部 374 個案例執行窮舉修復驗證，達成 100% 修復通過率。

3. **實作殘餘二部圖 BFS 最短增廣鏈修復與 $O(1)$ 預計算查找表**：
   * 參考作業研究領域針對 Nurse Scheduling Problem (NSP) 之動態重排文獻，於 `src/contingency.py` 實作 `IncrementalRepairEngine`：以廣度優先搜尋（BFS）在當前班表的殘餘二部圖上尋找從「空缺日」到「未滿 2 天配額員工」的最短交替路徑（Shortest Alternating Path），嚴格保證變動天數（漢明距離）最小。
   * 同時實作 `RobustScheduleSelector`，從 34 組班表中選出韌性最佳的基準班表 `Mon:A | Tue:C | Wed:A | Thu:B | Fri:D`（任何值班者臨時請假皆可 **100% 以 1-Hop 直接代班解決，0 次連鎖換班**），並預先編譯為 `ContingencyTable` 達成線上 **$O(1)$（`~0.21 us`）** 零延遲查表。

4. **跨語言雙軌極致最佳化（Python 平坦化 Tuple + C11 Bitboard/SWAR 原生引擎）**：
   * **Python 端優化 (`src/solvers.py`)**：移除遞迴熱路徑內的動態 `sorted()` 與字典複製，改於 `__init__` 預編譯為平坦不可變 Tuple，使 Python 單解耗時由 `27.50 us` 降至 **`9.93 ~ 14.91 us`**。
   * **C11 原生端實作 (`src_native/fast_scheduler.c`)**：參考 GitHub 開源西洋棋引擎 `Stockfish` 之 Bitboard 與 `yb303/swar`（SIMD Within A Register）技術，將 4 位員工的已排班天數打包進單一 `uint32_t` 暫存器（每員工佔 4 bits），以單週期位元加法 `c + (1U << (emp * 4))` 與遮罩位移取代陣列讀寫，在 `MSVC /O2` 下將單解搜尋壓縮至 **`16.98 ~ 20.22 ns`（比 Python 快逾 585 ~ 800 倍）**、全 34 解枚舉僅 **`95.10 ~ 122.54 ns`**！
   * **擴展性補強**：針對考題簡報「$n$ 位員工」新增 `test_07_general_n_employees_scalability`（$n=50$ 人測試），7 項單元測試全數 `OK`。
