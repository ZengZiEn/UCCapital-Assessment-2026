3.1 為什麼採用「Python 3.12 + C11 (/O2)」雙軌制架構？

在量化交易與高頻交易（HFT）團隊中，研究建模與自動化測試需要極致的表達力與可維護性（Python 的強項）， 而實盤熱路徑（Hot Path）則需要奈秒級反應、暫存器位元平行運算與 L1/L2 快取親和性（C/C++ 的強項）。 若只交 Python，執行速度受限於直譯器；若只交 C 語言位元運算，則領域擴充性較低。因此我們決定採用雙軌制架構：

3.2 七階段問題發現與工程決策對照表

順序思考階段當時面對的核心問題（Why）採取的工程決策與架構設計（How）量化驗證成果（Result）
Step 1考題逆向拆解與基準設定簡報含 3 道跨領域題目與 1 張無數值色塊圖，如何在動手前抓出隱藏考點？先以程式解壓 PPTX XML 與內嵌 PNG（發現為 575×313 Excel 9×5 表格），確立每題皆須同時交付「高可維護架構」與「極致效能實證」。精準鎖定三題核心與跨題同構關聯
Step 2導入標準軟體工程生命週期 (SDLC)如何避免面試作業寫成難以維護的單檔義大利麵程式碼？為三題建立對稱的五階段目錄：docs/01~04 → src/ → src_native/ → tests/ → scripts/ → results/。三個子專案結構 100% 對稱統一
Step 3參考 GitHub 與學術界開源架構閉門造車容易忽略業界成熟解法，開源社群如何解排班與自訂 malloc？調研 Google OR-Tools、ALNS 殘餘網路修復、Linux Slab Allocator、dlmalloc 與 GitHub mattconte/tlsf、Stockfish Bitboards。將業界頂尖資料結構直接融入三題設計
Step 4堅持實證主義（先實跑驗證再出報告）手算或未經編譯器實測的數據可能失真，如何確保報告 100% 可信？強制規定每題修改後必先通過單元測試與 Benchmark；在實跑中發現 Q1 全解空間實為 34 組（非手算 18 組），並修復 Q2 4 MB 區塊 VirtualFree 卸載後二次讀取問題與 Q3 動態卡方計算。全專案 18 項單元測試與 214 萬次壓力測試 100% 通過
Step 5反思語言選擇：建立 Python + C11 雙軌極速引擎Python 雖好維護，但直譯器開銷是否會讓執行效率尚未達到硬體極限？保留 Python 3.12 作為領域模型與測試框架，同時為 Q1 與 Q3 增建 C11 (MSVC /O2) 暫存器級原生引擎，並升級 Q2 為顯式自由串列。Q1 單解達 20.2 ns；Q3 百萬次洗牌僅 104.1 ms
Step 6建立完整可追溯日誌與考題逐字核對面試官追問「為什麼這樣改」或「n 位員工怎麼辦」時如何舉證？建立全時間軸 DEVELOPMENT_LOG.md；針對「n 位員工」新增 n=50 擴展測試；針對題目三新增「下一列 (Row 9) 馬可夫規律預測器」。每次修改皆有時間戳記與前後數據對照
Step 7視覺化雙 PDF 產出與目錄收斂整理如何讓評審在 3 分鐘內看懂技術深度，且打開資料夾時乾淨不雜亂？將支援文件與建置工具收納至 docs_and_tools/，清除所有 .obj 與 __pycache__，於根目錄呈現最乾淨的雙 PDF 報告與三題主目錄。根目錄清爽直觀，一鍵即可重現全流程
