2. 題目一：排班問題

2.1 問題定義

公司有員工 A、B、C、D，每週工作 Mon～Fri。規則：(1) 每天必須恰有一人上班；(2) 每人每週最多上 2 天，且只能排在自己有空的日子； (3) 排好班表後，可能有一位員工臨時表示某一天（原本有空的一天）不能上班，系統必須能快速應變。

總需求 5 人日、總供給上限 4 × 2 = 8 人日，因此有 3 人日的緩衝。但 Mon、Wed、Thu、Fri 各只有 2 人可上，屬於高度受限的日子，是演算法設計的關鍵。

2.2 演算法一：位元遮罩 + MRV 啟發式回溯法

每位員工的可用日預先編譯為 5-bit 整數（例如 A = 0b00111），判斷「某人某天是否有空」只需一次位元運算。 搜尋時採用 MRV（Minimum Remaining Values）原則：先決定可選人數最少的日子，並優先嘗試目前工時較少的員工以平衡負載。 本例只展開 5 個搜尋節點就找到可行解，沒有任何失敗回溯；平均耗時 9.9 µs（重複 2,000 次取平均）。

2.3 演算法二：Dinic 網路最大流

建立容量網路：源點 S → 員工（容量 2）→ 有空的工作日（容量 1）→ 匯點 T（容量 1）。若最大流等於 5，則流量為 1 的「員工→工作日」邊即構成合法班表。 時間複雜度 O(E√V)，能保證員工數擴大到數百、數千人時仍在多項式時間內求解。

2.4 突發狀況：員工臨時請假的最小變動修復

若每次請假都重新做全域排班，新班表可能與原班表差異很大，連沒請假的人也要改班。因此修復的目標是最小化變動天數（漢明距離）：

  • 0-Hop：請假者當天本來就沒有排班 → 班表不變。
  • 1-Hop：找當天有空且本週未滿 2 天的同事直接代班 → 變動 1 天。
  • k-Hop：若有空的同事都已滿 2 天，以 BFS 在殘餘圖上找最短交替鏈（空缺日 → 已滿額員工 Y → Y 的另一天 → 有餘裕的員工 Z），BFS 保證鏈最短，即變動天數最少。

此外，在班表發布前就對所有「(員工, 有空的日子)」組合預先算好修復方案存入雜湊表，線上發生請假時直接 O(1) 查表。

3. 題目二：C 語言 malloc 效能問題

3.1 為什麼反覆 malloc / free 會慢？

瓶頸說明
通用搜尋成本標準配置器必須支援任意大小，需走訪空閒串列 / bins，並在釋放時做分割與合併
系統呼叫與分頁40,000 Bytes 屬中大型區塊，超出許多實作的小物件快取，可能觸發向作業系統要記憶體、分頁錯誤與清零
鎖競爭標準 malloc 必須執行緒安全，每次呼叫都有加鎖或原子操作成本
碎裂化大小與生命週期交錯的配置使 heap 碎裂，搜尋時間隨執行時間變長
快取局部性每次取得的位址不保證在 L1/L2 快取中，造成 cache miss 與 TLB miss

3.2 改善策略

應用層：若大小固定，最簡單有效的做法是把配置移出迴圈重複使用緩衝區。配置器層：設計 myMalloc()，以「預先配置 + 自行管理」取代每次向系統要記憶體：

配置器層級 / 演算法分配複雜度釋放與合併複雜度核心資料結構與開源設計參考
標準 C malloc / freeO(B) 搜尋 + SyscallO(1) ~ O(N) + 鎖競爭系統通用堆積，40KB 大區塊易觸發核心態轉換與分頁清零
Tier-1：侵入式 LIFO Slab 池嚴格 O(1) (2 條指令)嚴格 O(1) (2 條指令)單向侵入式串列 (Intrusive Free-List)，剛釋放區塊駐留 L1/L2 熱快取
Tier-2：顯式雙向自由串列 ArenaO(1) 取首個可用空閒塊嚴格 O(1) 雙向邊界合併參考 dlmalloc / TLSF：Payload 內嵌 free_prev/next，完全跳過已分配塊

4. 題目三：分析歸納題

4.1 從圖檔還原資料

不靠肉眼數格子，而是以純 Python 解析簡報內嵌的 PNG（575×313 px，RGBA），完整實作 PNG 的五種掃描線濾波還原（含 Paeth）， 在 9×5 網格中心取樣，得到 45 格四色矩陣。四種顏色恰為 Office 標準色：紅 #FF0000、黃 #FFC000、綠 #70AD47、藍 #0070C0。

4.2 規則一：上下左右相鄰永不同色（正交著色）

網格共有 36 條水平相鄰邊與 40 條垂直相鄰邊，程式逐一檢查後同色相鄰數為 0。 為確認這不是巧合，固定各色數量後以 Python 隨機洗牌 50,000 次，並以 C11（xorshift64* + Daniel Lemire 無除法範圍映射）再執行 1,000,000 次（僅耗時 174.3 ms，每 5 萬次僅 8.72 ms）：平均有 17.96 條衝突，最少也有 3～4 條， 百萬次隨機排列中零衝突出現 0 次。

4.3 規則二：右側三欄的鏡像「三明治」結構

從 Row 2 到 Row 8 連續 7 列，Col 2 與 Col 4 完全相同，右三欄形成 X-Y-X 的對稱結構（B-G-B、R-Y-R、Y-R-Y…）。 在水平不相鄰的前提下，Col 4 只能從「不等於 Col 3」的 3 種顏色中選，剛好等於 Col 2 的機率為 1/3；若各列獨立，連續 7 列都成立的機率約為 (1/3)7 = 0.000457（約 1/2187）。前兩列 Row 0、Row 1 不符合，兩者的 Col2/Col4 剛好是 (G, Y) 與 (Y, G) 互換。

4.4 規則三、四：數量配額與棋盤奇偶平衡

全圖數量為 R 10、Y 10、G 13、B 12， 資訊熵 1.9904 bits（最大值 2），分布非常均勻。每一欄都包含 4 種顏色，任何顏色在單一列或單一欄中最多出現 3 次。 若依 (row+col) 奇偶把格子分成西洋棋盤的黑白兩組，紅與黃在兩組中都剛好各 5 格。

4.5 規則五：水平與垂直的轉移偏好不同（方向異向性）

把相鄰兩色視為一次「轉移」。水平方向中，同色系配對（冷色 B-G、暖色 R-Y）佔 58.3%， 垂直方向只佔 27.5%；其中 R-Y 在水平佔 25.0%，在垂直只佔 7.5%。 以 2×2 列聯表做卡方檢定得 χ² = 7.39（自由度 1，臨界值 6.63 對應 p = 0.01）。

4.6 規則六：列與列的相似度，以及與題目一的呼應

計算任兩列之間不同的格數（漢明距離），Row 1 與 Row 5（差 1 格）、Row 6 與 Row 8（差 1 格），幾乎是同一列只換一格。 若把 5 欄看成 Mon～Fri、4 色看成 4 位員工、9 列看成 9 週，這張圖就是一份「沒有人連續兩天上班（水平不同色）、同一個星期幾不會連兩週同一人（垂直不同色）」的輪班表； 相鄰週只改一格，也正對應題目一「臨時請假只需變動 1 天」的思路。進一步結合歸納出的規則（與 Row 8 正交不同色 + 右三欄 Col2=Col4 鏡像對稱 + 馬可夫轉移適合度評分），演算法可自動推演出最可能出現的下一列（Row 9）：Top 1: R-G-B-G-B (適合度 1.9611)；Top 2: G-B-Y-R-Y (適合度 1.9167)；Top 3: B-G-Y-R-Y (適合度 1.8694)。

題目一技術限制

  • C11 Bitboard/SWAR 原生引擎已將單解耗時壓縮至 ~17.0 ns、全枚舉 ~95.1 ns；Python 引擎計時已重複 2,000 次取平均，Dinic 耗時包含建圖，在小規模（4 人 5 天）下比 MRV 慢屬正常，其價值在於大規模擴展時的多項式時間保證。
  • 「最小變動」是針對單一請假事件、以增廣鏈長度衡量；若同時多人請假或需考慮員工偏好，需改用最小成本流等方法。

題目二技術限制

  • myMalloc 目前為單執行緒設計（未加鎖）；多執行緒環境需加入 thread-local cache（如 tcmalloc 架構）或鎖。
  • Tier-2 Arena 已升級為侵入式顯式雙向自由串列（Explicit Doubly-Linked Free-List），分配時完全跳過已分配區塊且雙向合併為 O(1)；若空閒區塊尺寸高度碎片化，可再加一層依 2 的冪次分箱之二級位元圖索引（完整 TLSF）以保證最壞情況 O(1)。
  • 場景 1、2 是記憶體池最擅長的「同尺寸、LIFO」工作負載；Double-Free 偵測依賴 Header Magic，能攔截池內常駐區塊的重複釋放。

題目三技術限制

  • C11 蒙地卡羅 1,000,000 次中 0 次命中，依統計三法則（Rule of Three）在 95% 信賴水準下可嚴格推得 p < 3×10-6；報告中的 3.2e-10 則是以獨立近似估算的理論量級。鏡像對稱的 1/2187 假設各列獨立；「與題目一同構」為合理解讀與應用展示。
