# 題目一：排班問題 — 需求分析、文獻參考與演算法建模 (`01_analysis.md`)

## 1. 題目背景與需求拆解

### 1.1 原始題目描述
某公司有 $n$ 位員工（如：`A`、`B`、`C`、`D`），一週上班日為 `Mon` ~ `Fri`（共 5 天）。
每位員工會給出一週中有「可以上班」的日子，範例如下：
* **A**：`Mon`, `Tue`, `Wed`
* **B**：`Mon`, `Thu`, `Fri`
* **C**：`Tue`, `Wed`, `Thu`
* **D**：`Tue`, `Fri`

### 1.2 核心規則與目標（Hard & Soft Constraints）
1. **每日覆蓋限制（Daily Coverage Constraint）**：一週內 `Mon` ~ `Fri`，每天必須有一個人上班（不能沒人開天窗）。
2. **個人工時上限與可用性限制（Capacity & Availability Constraint）**：
   * 每個員工一週 **最多只能上班 2 天**（$\le 2$ 天）。
   * 只可以在員工「有空的日子」排他上班。
3. **突發狀況動態應變（Dynamic Disruption & Rescheduling）**：
   * 在排好班表後，可能會有一位員工臨時說：**『這週我有某一天不能上了』**（這一天是他原本有空、甚至已被排班的某一天）。
   * 系統必須能快速給出應變方案（重新指派替代人選或進行最小幅度的換班修復），若遇到理論上無解的極端情況，亦須明確偵測並回報原因。

## 2. 產業實務與 GitHub 開源方法參考

在作業研究（Operations Research, OR）與高頻交易系統資源調度領域，此問題屬於經典的 **員工排班問題（Employee Rostering / Nurse Scheduling Problem, NSP）** 結合 **動態重排與局部修復（Dynamic Rescheduling & Perturbation Repair）**。參考 GitHub 上的開源實作（如 `google/or-tools` 的 Network Flow / CP-SAT 範例，以及學術界針對 NSP 的 `Construct-Perturb-Repair` 架構），常見解法可歸納為以下三大流派：

### 2.1 流派一：網路最大流／二部圖多重匹配（Max-Flow / Bipartite B-Matching）
* **原理**：將問題轉換為有向容量網路 $G = (V, E)$：
  * 源點 $S$ 連向每位員工 $e_i$，邊容量 $\text{cap}(S, e_i) = 2$（每人每週最多上 2 天）。
  * 若員工 $e_i$ 在日子 $d_j$ 有空，建立邊 $(e_i, d_j)$，容量 $\text{cap}(e_i, d_j) = 1$。
  * 每個工作日 $d_j$ 連向匯點 $T$，邊容量 $\text{cap}(d_j, T) = 1$（每天需 1 人值班）。
* **演算法**：使用 **Dinic 演算法（Dinic's Algorithm）** 或 **Edmonds-Karp** 求解最大流。若最大流 $F_{\max} = 5$，則所有流經 $(e_i, d_j)$ 且流量為 1 的邊即構成合法班表。
* **時間複雜度**：在單位網路（Unit Network）或小容量二部圖上，Dinic 演算法複雜度為 $O(E \sqrt{V})$，即便員工數擴展至數千人，依然能在毫秒內求解。
* **突發狀況優勢**：當員工 $e_i$ 在第 $d_j$ 天臨時請假時，只需移除邊 $(e_i, d_j)$ 並在**殘餘網路（Residual Graph）**上尋找一條從 $S$ 到 $d_j$ 的增廣路徑（Augmenting Path），即可在 $O(V + E)$ 時間內完成局部修復！

### 2.2 流派二：位元遮罩狀態壓縮回溯法 + 最小剩餘價值啟發式（Bitmask Backtracking + MRV Heuristic）
* **原理**：針對中小型規模或需要**枚舉所有可行班表**以評估「班表魯棒性（Robustness）」的場景，採用約束滿足問題（CSP）的回溯搜尋：
  * **位元遮罩（Bitmask）**：將每位員工的可上班日編碼為 5-bit 整數（例如 `Mon=1<<0`, ..., `Fri=1<<4`），利用 CPU 位元運算加速可用性檢查。
  * **MRV（Minimum Remaining Values，最小剩餘價值／最受限變數優先）**：優先排「可選員工最少」的日子。例如範例中：
    * `Mon`：僅 A, B 可上（2 人）
    * `Wed`：僅 A, C 可上（2 人）
    * `Thu`：僅 B, C 可上（2 人）
    * `Fri`：僅 B, D 可上（2 人）
    * `Tue`：A, C, D 皆可上（3 人）
    先排高度受限的日子，可大幅剪枝（Pruning）搜尋樹。

### 2.3 流派三：局部擾動修復與預計算應變表（Perturbation Repair & Pre-computed Contingency Table）
* **最小變動原則（Minimal Perturbation / Minimum Hamming Distance）**：
  在真實企業排班中，臨時改班若牽動太多人會造成營運混亂。因此修復目標是最小化「班表變動天數（Hamming Distance）」：
  1. **0-Hop（無須變動，成本 0）**：請假員工當天本來就沒排班，原班表直接維持。
  2. **1-Hop（直接代班，變動 1 天）**：由另一位當天有空、且本週排班數 $< 2$ 的員工直接頂替。
  3. **2-Hop（連鎖換班，變動 2 天）**：當天有空的替代員工 $Y$ 本週已滿 2 天，但 $Y$ 在另一天 $d'$ 的班可以交給尚未滿 2 天的員工 $Z$，從而讓 $Y$ 空出配額來頂替第 $d$ 天。
  4. **預計算 `O(1)` 應變查找表（Contingency Lookup Table）**：在排班確立時，預先針對所有 `(員工, 請假日)` 組合算好最佳替代方案並存入雜湊表，突發狀況發生時查詢時間複雜度為嚴格的 **$O(1)$**。

## 3. 範例資料之數學特性深度剖析

針對題目給定的範例：
* 總需求天數 $= 5$ 天（`Mon` ~ `Fri`）。
* 員工共有 4 人（`A, B, C, D`），每人上限 2 天，總供給上限 $= 4 \times 2 = 8$ 人日。
* 各日可用員工分布：
  * `Mon`: `{A, B}` (2 人)
  * `Tue`: `{A, C, D}` (3 人)
  * `Wed`: `{A, C}` (2 人)
  * `Thu`: `{B, C}` (2 人)
  * `Fri`: `{B, D}` (2 人)

### 3.1 關鍵結構洞察：子集瓶頸（Hall's Marriage Theorem 視角）
觀察 `{Mon, Wed, Thu}` 這三天：
* `Mon` 只能由 `{A, B}` 上
* `Wed` 只能由 `{A, C}` 上
* `Thu` 只能由 `{B, C}` 上
* 注意 `D` 在 `{Mon, Wed, Thu}` 完全沒空！這意味著 `{Mon, Wed, Thu}` 這 3 天完全由 `{A, B, C}` 分擔。
* 更進一步看，全週 5 天中，若移除任何可行邊，都能透過其它人尚未用滿的配額（總配額 8 人日 $>$ 5 人日，有 3 人日的緩衝餘裕 Slack）進行 1-Hop 或 2-Hop 修復！
* 經由我們的演算法完整枚舉，此範例共有 **34 組合法初始班表**，且對於任意一組合法班表與任意單日臨時請假事件（共 $34 \times 11 = 374$ 個突發測試案例），**100% 存在合法修復解（其中最佳基準班表在所有請假事件下皆僅需變動 1 天即可完成 1-Hop 直接代班）**！
